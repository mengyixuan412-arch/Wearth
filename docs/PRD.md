## 1. 产品定位

**一句话定位:把"衣橱资产"和"购买决策"打通的个人衣橱工具 —— 已经买的帮你穿够本,还没买的帮你判断值不值。**

| 维度 | 描述 |
|---|---|
| **用户** | 以女性为主,衣橱有一定规模(30 件以上)、每月有服饰消费、对穿搭有要求但也常后悔剁手 |
| **场景** | ① 衣服堆进衣柜,利用率低且被遗忘→整理录入<br>② 购衣花费高昂,却依然忍不住剁手→CPW 提醒<br>③ 刷到心动单品,不确定该不该下单→决策助理 |
| **问题** | 衣橱是一笔看不见的资产 —— 花了多少钱不知道、买了什么记不住、穿没穿够本没感觉,于是继续冲动买、继续闲置 |

**核心机制:真实穿着成本 CPW = (购买价格成本 + 累计养护支出) ÷ 累计穿着次数。**

这是把"消费"和"衣橱"连起来的那根线,所有模块都围绕它转:

```
录入(定分子) → 日历(定分母) → 养护(补分子) → 统计(看结果) → 决策(预测未来的 CPW)
```

**产品立场:我们站在用户钱包这一边。** 不做电商导流、不做分成返佣 —— 决策模块的目标函数是"帮你少买错",不是"帮你多下单"。这是我们和市面上所有衣橱产品最根本的区别,也是所有功能取舍的第一原则。

## 2. 用户画像

MVP 优先聚焦女性用户。品类体系、UI 调性、决策评分逻辑均按女性服饰特点设计(裙装/连体装细分、材质敏感度更高、单品数量更多)。

| | A. 冲动囤衣型 | B. 精算极简型 | C. 通勤穿搭焦虑型 |
|---|---|---|---|
| 画像 | 24–30 岁女性,一线/新一线 | 28–38 岁女性 | 22–28 岁女性,职场 1–3 年 |
| 月服饰支出 | 1000–3000 元 | 500–1500 元 | 500–1500 元 |
| 行为特征 | 直播间/小红书种草即下单,衣橱塞满但常穿的就那 20% | 追求胶囊衣橱,买前反复比价,在意材质和耐穿度 | 衣服不多,纠结穿什么,怕穿错场合 |
| 核心诉求 | 我到底花了多少钱?还有必要再买吗? | 我想知道每件衣服的真实性价比 | 我想把手上的衣服穿出更多花样 |
| 优先级 | **P0(主要目标用户)** | **P0** | P1 |

MVP 优先服务 A + B —— 她们对"钱"和"利用率"有痛感,是决策模块的天然使用者。C 的搭配推荐诉求放到后续版本。

## 3. 用户痛点

1. **衣橱不可见** —— 记不清自己有什么,导致重复购买(三件几乎一样的白衬衫)、旧衣被遗忘在衣柜深处。
2. **消费无感知** —— 单次 300 元感觉不贵,一年下来算总账才吓一跳。没有工具把"服饰支出"单独归集到具体单品上。
3. **冲动型决策** —— 详情页、直播间的即时刺激很强,而"我衣橱里有没有类似的""这个材质好不好打理""能不能搭得起来"这些理性信息在下单那一刻是缺失的。

## 4. 问题现状

| 现有做法 | 做法说明 | 局限 |
|---|---|---|
| 手机相册 + 备忘录 | 拍照存相册,用备忘录记品牌价格 | 图片和文字割裂,无法统计,查找靠翻 |
| Excel / 记账 App | 手动记录每笔服饰支出 | 只有金额没有实物,不知道"这笔钱穿出来了没有" |
| 小红书 OOTD / 衣橱盘点笔记 | 发帖记录每日穿搭、年度衣橱复盘;养护知识也主要来自这里 | 靠社交动力驱动,不可持续;数据不沉淀;养护知识看完就忘,用时找不到 |
| 现有衣橱 App | 录入单品、AI 搭配、记穿搭日记 | 见下方竞品分析 |
| 买前问闺蜜 / 翻评论区买家秀 | 依赖他人主观意见 | 与"我自己的身材、衣橱、预算"无关,建议不个性化 |

**共性缺口:记录端(衣橱)和消费端(决策)是两套割裂的系统。没有任何工具把"我已经拥有什么"变成"我该不该再买"的依据 —— 而这恰恰是最该被数据化的一步。**

## 5. 竞品分析

### 5.1 尽简衣橱 —— 功能纯粹，聚焦整理
- **定位**:电子衣橱管理助手。
- **录入**：拍照、从相册添加、从相册批量添加、从网页导入、从剪贴板粘贴
- **功能**：
 - **衣橱tab**：搜索单品、添加单品、切换视图、显示设置、分类管理
 - **搭配tab**：工作、休闲、派对、正式、度假、运动、居家多个场景
 - **日历tab**：添加天气、日记、搭配、单品
 - **灵感tab**：随想集记录灵感
 - **设置tab**：衣橱统计、数据备份、衣橱管理、选项管理、货币管理、身材尺码等
- **借鉴**:分类体系细致且允许自定义;每日穿搭记录交互路径短;产品较轻不打扰。
- **不足**:只做"整理"不做"消费" —— 价格可录入,但只是展示字段,不参与任何计算;没有购买决策环节,只解决"已买",不解决"要买"。

### 5.2 搭搭 —— AI 强大，穿搭社区
- **定位**:AI 智能电子衣橱,主打搭配 + 社区。四大功能:搜索搭配、自动搭配、穿搭规划、分享穿搭。用户可完善身材档案,与身材相近的用户互相看穿搭。
- **录入**:同款导入（衣服库）、相册上传、拍照上传、淘宝导入
- **功能**:
  - **主页**:AI搭配、帮我搭配、搭配DIY、穿搭日记、穿搭测评、拍照搜搭配、邀请有礼、会员中心
  - **衣橱**分类摆放、上传衣服
  - **搭配**我的搭配、ai帮搭配
  - **发现**发现（帖子-类似小红书排版）、关注
  - **我的**我的动态、我的相册、个人档案、我的收藏、我的点赞、我的消息、我的券包等
- **借鉴**:
  - **AI 录入能力**:支持批量上传 + 批量抠图，AI 自动识别品类、颜色、季节、材质并预填。
  - **身材档案匹配**:按身材相近推荐穿搭,是个聪明的冷启动解法。
- **不足**:
  - 和小红书的社区定位重合，重心在搭配和社交,**无买前决策**这一环。
  - 价格可录入,但只是展示字段,不参与任何计算。
  - 支持添加购买链接、社区种草,**刺激消费**与"理性消费"的诉求相反。
- **提示**:搭搭在衣橱管理这一层的功能已相当完整,我们不应在"整理 + 搭配"上和它正面竞争,差异化必须落在**决策 + CPW 闭环**上。

### 5.3 Lookie —— 淘宝生态的导购型衣橱
- **定位**:淘宝出品(杭州万象创想科技)的 AI 电子衣橱,一键导入淘宝订单生成衣橱、AI 搭配、数字分身虚拟试穿,可跳转淘宝购买同款。
- **录入**:相册上传、拍照上传、淘宝导入
- **功能**:
  - **首页**:穿搭日记、穿搭测试、自由试穿、发型发色、AI写真、AI帮我搭、商品流推荐
  - **衣橱**导入衣橱、DIY搭配、AI搭配
  - **圈子**关注、全部、搭配、投票
  - **我的**生成历史（试穿、试戴、发型发色、AI写真、AI视频）、收藏、发布、OOTD、搭配等
- **借鉴**:
  - **订单导入**。用户网购的衣服本来就有订单数据(图片、价格、品牌、购买日期、尺码全都有),导入即录入。这是我们能想到的最优录入路径。
  - 衣橱支持按穿着频率排序,说明"利用率"是普遍诉求。
- **不足**:
  - 商业模式决定了它的目标是**让你买更多** —— 展示风格化商品、跳转淘宝购买,衣橱只是导流的入口。
  - 覆盖淘宝生态的衣服，线下购买、其他平台的衣服录入体验回落到普通水平。
  - 价格可录入,但只是展示字段,不参与任何计算;没有购买决策,不解决"钱花得值不值"。

### 5.4 替代方案参考
- **小红书**:实际承担了大量"衣橱盘点/OOTD/养护知识"需求,但是内容社区不是工具,数据不沉淀,知识用时找不到。
- **记账类 App**:能统计服饰支出总额,但和具体单品脱钩,无法回答"这件衣服值不值"。

### 5.5 差异化

| 维度 | 尽简衣橱 | 搭搭 | Lookie | **Wearth** |
|---|---|---|---|---|
| 核心指标 | 单品数、搭配数 | 搭配数、社区互动 | 商品曝光 | **CPW(真实穿着成本)** |
| 数据用途 | 展示 | 展示 + 搭配 | 导流 | **喂给购买决策** |
| 价格数据 | 可录入,仅展示 | 可录入,仅展示 | 可录入,仅展示 | **参与 CPW 计算,喂给决策** |
| 买前决策 | 无 | 无 | 有(但引导你买) | **有(帮你少买错)** |
| 商业立场 | 中立 | 会员订阅;内容仍种草 | 明确导购 | **明确站在用户钱包一侧** |
| 养护知识 | 无 | 无 | 无 | **养护支出记账 + 养护建议** |

**一句话:市面上的衣橱产品都在帮你"买得多、搭得多",没有人帮你"买得对、穿回本"。**

## 6. 功能设计

### 6.1 核心流程
```
录入衣服(衣服拍照→API抠图→AI预填信息)
        ↓
日历记录:上传当日 OOTD 全身照 → 关联衣橱单品 → 穿着次数自动 +1,CPW 计算
        ↓
养护记录:记一笔干洗支出,计入 CPW 分子
        ↓
统计看板:总花费 / CPW 最值榜 / 本季还没穿过 / 品牌排名
        ↓
消费决策 → 上传商品图 + 详情页截图 → 决策评分 → 买/不买
```

### 6.2 模块一:单品录入

| 功能 | 优先级 | 说明 |
|---|---|---|
| 拍照/上传图片 | P0 | 相机拍摄与本地上传,**V1.0 单张** |
| 批量上传 | P1 | 一次最多 9 张 |
| 自动抠图 | P0 | 调用第三方抠图 API 去背景,生成透明底单品图;支持手动微调/跳过 |
| **AI 智能预填** | P0 | 上传后由大模型自动识别并预填:品类、子品类、颜色、季节、风格标签。用户只需确认或改。**材质不做纯图片识别**(不可靠),改为**拍水洗标做 OCR 提取** —— 与决策模块的详情页截图提取复用同一套视觉调用,边际成本极低,且这是材质数据唯一可靠的来源 |
| 信息填写 | P0 | **必填**:品类(两级)、价格、购买日期<br>**选填**:品牌、材质成分、颜色、季节、尺码、购买渠道、备注<br>**材质成分为结构化数据**(成分名 + 百分比的列表,如 羊毛 70% / 聚酯纤维 30%),不是一行自由文本 —— 决策模块的"材质与养护"维度要按成分逐项打分 |
| 扩展字段 | P1 | 存放位置、商品链接 |
| 分步录入 | P0 | 允许只填必填项先入库,后续在详情页补全。**录入是衣橱页上的弹窗,不是独立页面** —— 录完落回原来的网格位置,不打断"翻衣橱"这件事 |
| 单品详情页 | P0 | 从右侧滑入的抽屉(不是独立路由 —— 翻单品是"瞄一眼再回去"的动作,整页转场会把列表的滚动位置和筛选状态都冲掉)。含图片、全部属性(可就地编辑)、累计穿着次数、当前 CPW、穿着状态、养护记录(可增删改)、穿搭日志关联 |
| 穿搭日志关联 | P0 | 在详情页直接把这件关联到某一天:浮层里给出穿搭日志那张日历的缩印版,格子里放当天的 OOTD 照片,点哪天是看着定的。关联后穿着次数 +1,CPW 重算 |
| 衣橱列表 | P0 | 网格视图,按品类/季节/颜色/品牌/状态筛选,按 CPW/穿着次数/价格/购入时间排序 |
| 状态管理 | P0 | 在用 / 闲置 / 已处置(送人、卖出、丢弃);已处置不计入在用统计,但保留在历史花费中 |

> **设计原则:录入速度是这个产品的生死线。** 三家竞品均提供批量上传与平台导入,V1.0 只做单张上传 + AI 预填,录入效率明确落后;同款导入需自建单品库,我们无数据来源,不纳入规划;批量上传与链接导入在 V1.1 补齐。单件录入(含拍照)控制在 30 秒内。

### 6.3 模块二:个人信息

| 功能 | 优先级 | 说明 |
|---|---|---|
| 基础信息 | P0 | 年龄、常驻城市 |
| 参考照片 | P0 | 一张清晰全身照。作为身材与肤色的参照,也是肤色取色的取样源 |
| 风格偏好 | P0 | 从预设标签中多选(通勤/简约/复古/运动/甜美/中性/法式/山系…),随时调整 |
| 肤色选择 | P0 | 四档预设(白皙/自然/小麦/深)+ 自定义色值;可直接在参考照片上取色 |
| 身体数据 | P0 | 身高、体重(必填)+ 肩宽、胸围、腰围、臀围、大腿、小腿、鞋码 |
| 消费设定 | P0 | 月度服饰预算(用于决策模块的价格合理性判断) |

> 每个字段都有下游用途,不做无用的注册表单:**肩宽/胸围/腰围/臀围** → 身材适配度评分(附录 D-⑤);城市 → 关联当地气候判断季节适用性;预算 → 价格合理性评分;**肤色 → 身材与肤色适配度评分的 5b 子项**(附录 D-⑤)。
>
> 大腿、小腿、鞋码不参与评分,只作用户自己的尺码备查 —— 它们对应的品类(裤装的腿围、鞋)没有可靠的公开尺码表口径。**职业字段已移除**:它原本要支撑"场合适配",而场合标签本身推迟到 V1.1,留着就是一个没有下游的字段。

### 6.4 模块三:穿搭日历

**入口设计:以 OOTD 全身照为主对象,单品关联为第二步。**

| 功能 | 优先级 | 说明 |
|---|---|---|
| 月视图日历 | P0 | 每天一格,有记录的日期显示当天 OOTD 缩略图,形成"穿搭相册"的视觉积累 |
| 记录当日穿搭 | P0 | 点击日期 → **上传/拍摄当日 OOTD 全身照** → 从衣橱中多选本次穿着的单品进行关联 → 保存 |
| 文字备注 | P0 | 一句话记下当天的搭配想法或场合 |
| 语音备注 | P1 | 直接说一句话代替打字,存本地(webm/opus),可回放与删除。它服务的是北极星指标 —— 记录门槛越低,周记录天数越高 |
| 扩展字段 | P1 | 场合标签、天气、心情 |
| 自动计数 | P0 | 保存后,所关联单品的穿着次数 +1,CPW 自动重算 |
| 即时反馈 | P0 | 保存成功后展示:"本次穿搭让 3 件单品的平均 CPW 下降了 ¥X" —— 把记录行为变成正反馈,这是留存的关键 |
| 关联提醒 | P1 | 首页提示"你有 3 天的穿搭还没关联单品",一键补关联。**"先传照片、稍后关联"的能力 V1.0 就有,推迟的只是首页那个提醒入口** |
| 补记编辑 | P0 | 支持补记过去日期、编辑/删除记录(计数同步回滚) |

> 设计取舍:拍一张全身照比逐件勾选单品轻松得多,先降低记录门槛拿到用户的坚持;单品关联作为第二步,用"待关联"待办和 CPW 反馈来牵引用户补全。

### 6.5 模块四:统计看板

| 功能 | 优先级 | 说明 |
|---|---|---|
| 总览卡片 | P0 | 单品总数、衣橱累计购买支出、累计穿着次数、衣橱平均 CPW |
| 花费统计 | P0 | 按月/年的服饰支出趋势(区分购买支出与养护支出);按品类的花费占比;与预算的对比 |
| 品牌排名 | P0 | 按花费金额 / 按件数 双维度排行 |
| 单品排行 | P0 | 最常穿 TOP10、CPW 最低 TOP10(最值)、CPW 最高 TOP10(最不值) |
| **本季还没穿过** | P0 | 季节标签含当季、且本季 0 次穿着的单品列表。**纯事实陈述,不做提醒、不加价值判断**。它补的是 CPW 榜的盲区 —— 从未穿过的单品 CPW 未定义,永远不会出现在 CPW 榜上(详见附录 C) |
| 结构分析 | P0 | 品类花费分布、颜色分布、季节分布(用于发现"你有 8 件黑色上衣"这类结构失衡) |
| **支出趋势** | P0 | 按今年/本季/本月/全部四档区间切换,柱状图区分购买与养护;附环比读数("较去年同期上涨 4%")。总额答不上来的那个问题是"钱花在哪个月",这张图专答它 |
| **衣橱投入** | P0 | 累计投入 = 购买 + 养护,两项各自的金额与占比,以及本月预算的消耗;末尾挂最近一笔购入与最近一笔养护 |
| **衣橱规模** | P0 | 截至每个时间桶,手上还留着多少件的累计阶梯图。区分"买了多少"与"留下多少" |
| **穿着分布** | P0 | 各品类的累计穿着次数点阵,一眼看出穿得最多的是哪一类 |
| **在穿比例** | P0 | 每点一件单品、空心为尚未穿着。回答"衣橱里有多少件其实没在穿" |
| **单次成本区间** | P0 | 按 CPW 分档(<10 / 10–30 / 30–60 / 60–120 / ≥120 / 未穿)的件数直方图。均值背后的形状 —— 全衣橱压成一个数字,看不出它是怎么分布的 |

> **不做资产折旧**。总览只显示"累计购买支出",不按年限或穿着次数衰减。折旧规则难以定义、用户难以理解,而 CPW 已经承担了"这件衣服值不值"的判断职责。
>
> **不做分级分档**。只显示数值本身(如 ¥45/次),不加"优秀 / 良好 / 一般 / 待审视"标签,不做红黄绿的语气化配色。

### 6.6 模块五:购买评分

| 功能 | 优先级 | 说明 |
|---|---|---|
| 输入 | P0 | 上传商品主图 + 详情页截图(含尺码表、材质成分、价格) |
| 信息提取 | P0 | 由大模型从截图中识别价格、材质成分、尺码表;识别失败时降级为手填 |
| 评分触发 | P0 | **填完后按「生成评分报告」才出分,不跟着输入实时重算**。边填边跳分会把评分读成一个仪表盘 —— 用户盯着数字调价格、试品类,变成刷分而不是判断;而且决策记录存下来的必须是"按下那一刻"的那一份。信息改动后提示"重新生成以更新评分" |
| 评分输出 | P0 | 综合评分(0–100)+ 分维度得分与文字理由。**不输出购买建议** —— 决策主体是用户,产品只提供判断依据 |
| 评分维度 ①**衣橱重复度** | P0 | 衣橱中是否已有同品类/同色系/同风格的相似单品,列出具体是哪几件 |
| 评分维度 ②**可搭配能力** | P0 | 能与现有多少件单品组合,列出具体可搭配单品 |
| 评分维度 ③**价格合理性** | P0 | 与该品类历史均价、本月剩余预算对比;并**预估 CPW**(按同品类历史穿着频次推算) |
| 评分维度 ④**材质与养护** | P0 | 按成分评估穿着舒适度、耐久度与养护难度,并给出**年度预估养护成本** |
| 评分维度 ⑤**身材与肤色适配度** | P0 | 尺码表围度与用户围度比对(5a),商品色系与用户肤色的冷暖比对(5b)。5b 让鞋 / 包 / 帽子 / 首饰 / 配饰这些没有围度的品类也有分可算 |
| 尺码档记录 | P1 | 均码/XS/S/M/L/XL/XXL 选一档,随决策记录存档。**不参与计分** —— ⑤ 比的是尺码表上的围度数字,字母档只是说明"下面那几个围度是照哪个码抄的" |
| 清空商品信息 | P1 | 一键清空这张表(不动已传的截图),连同已生成的报告一起作废 —— 报告是照着这份表算的,表没了那个分就没有依据 |
| 决策记录保存 | P0 | 保存每次评分记录,可回看历史评分与当时的建议 |
| **报告追问对话** | P0 | 报告下方一条对话,只针对当前这份报告提问。上下文是本次的商品信息、分维度得分与佐证单品、衣橱快照、个人档案 —— 回答只能引用这些既有事实,不许现编衣橱里没有的单品、不许自己估价。**不给购买结论**(同 §8) |
| **假设性重算** | P0 | "降到 400 呢""换成 100% 羊毛呢"这类问题,由模型把自然语言解析成一组参数改动,交回规则引擎重跑,返回新的分维度得分。**模型只解析意图,分数仍由规则引擎出** |
| 一键转为衣橱单品 | P1 | 实际购买后把评分数据、图片、价格带入录入表单。用户看完评分不一定当下购买,转化时机与交互需另行设计 |
| 商品链接抓取 | P2 | 粘贴链接自动抓取商品信息。尽简衣橱已实现网页导入与剪贴板粘贴,说明路径可行,后续版本尝试 |
| 决策后验回访 | P2 | "当初评了 85 分,现在实际 CPW ¥12"。**需要追踪用户是否真的购买,行动路径复杂**,推迟 |

> **对话不改分数。** 追问与假设重算都不写回已生成的报告 —— 报告是"按下生成那一刻"的存档(见上"评分触发")。假设重算的结果只活在对话里并标注为假设值;用户认可后自己回去改商品信息、重新生成,决策记录里才会有新的那一份。
>
> **假设重算是这个功能和普通聊天框的分界。** 用户看完报告真正想问的不是"为什么扣分",是"如果便宜 100 呢"。让模型口算会得到一个和规则引擎对不上的数,评分就失去了一致性;交回规则引擎重跑,则模型只做意图解析、判断仍归规则 —— 这一步竞品做不到,因为它们没有规则引擎可回。
>
> **评分逻辑用规则引擎,大模型只负责截图理解和理由生成。** 这样分数稳定可复现,同一件商品两次评分不会给出不同结果 —— 决策工具的公信力建立在一致性上。
>
> **冷启动策略**:①②依赖衣橱数据,③的品类均价与 CPW 参照同样依赖衣橱;④⑤只看商品本身与用户身材,不受衣橱规模影响。衣橱少于 15 件时,输出④⑤两个维度与③的参考价路径,并提示"再录入 X 件衣服可解锁完整评分",把决策功能反过来变成录入的驱动力。

### 6.7 模块六:衣物养护

**设计原则:养护知识不做独立的内容频道,只做"上下文触发的提示"。**
用户不会主动打开一个百科去查,只有在她看着自己那件羊毛大衣的时候,养护建议才有意义。同时,养护延长衣服寿命 = 提高穿着次数 = 降低 CPW,这与产品内核完全自洽。

| 功能 | 优先级 | 说明 |
|---|---|---|
| **养护支出记账** | **P0** | 单品详情页添加养护记录(干洗/修补/护理,金额 + 日期 + 备注),计入 CPW 分子;统计中与购买支出分开展示。它是 CPW 公式的分子组成部分,不做则核心公式不完整 |
| 材质养护卡片 | P1 | 用户填写材质后,详情页自动展示该材质的养护要点(洗涤/晾晒/熨烫/收纳/禁忌)。内置约 20 种常见材质的静态建议表 |
| 养护成本预估 | P0 | 决策评分"材质与养护"维度输出年度预估养护成本(与模块五合并实现) |
| 单品养护问答 | P1 | 详情页"问问这件怎么护理",把品类/材质/颜色作为上下文交给大模型,回答"小白鞋发黄怎么办"这类**问题导向**的问题 —— 不建内容库,按需生成 |
| 换季养护提醒 | P1 | 换季时提醒"你有 5 件羊毛单品该收纳了",附对应材质的收纳要点 |

> 材质导向的知识(羊毛怎么洗)可结构化、可自动匹配,用静态表做;问题导向的知识(小白鞋发黄怎么办)长尾无穷,用大模型按需回答。这样既不用做内容运营,又能覆盖用户的真实问题。

## 7. V1.0 开发范围收敛

**收敛原则:影响数据模型的功能先做,纯展示层和体验优化的功能后做。**
前者后补要迁移数据、重算历史;后者随时能加,不影响已有数据。

| 模块 | **V1.0 做** | 推迟到 V1.1 / V2.0 |
|---|---|---|
| 录入 | 单张上传 + API 抠图 + AI 预填 + 水洗标 OCR + 必填三项 + 完整属性表单 + **状态管理** | 批量上传、存放位置、商品链接 |
| 个人信息 | 全部字段录入(含参考照片、肤色) | —— |
| 日历 | 月视图 + OOTD 上传 + 单品关联 + 自动计数 + 文字备注 + **语音备注** | 场合标签、天气、心情、待关联提醒的首页入口;**CPW 即时反馈(评估后不做)** |
| 统计 | 总览 + 花费统计 + 品牌排名 + 单品排行 + 本季还没穿过 + **结构分析** + 支出趋势 / 衣橱规模 / 穿着分布 / 在穿比例 / 单次成本区间 | —— |
| 决策 | 截图上传 + LLM 提取 + **主图识别品类/款式/颜色** + 规则评分(①②③④⑤)+ 决策记录 + 尺码档 + **报告追问 + 假设重算** | 一键转为衣橱单品、链接抓取、后验回访 |
| 养护 | **养护支出记账**(可增删改) | 材质养护卡片、养护问答、换季提醒 |
| 存储 | 本地存储 + **邮箱登录后云端同步**(见文末) | 分享、协作、多用户 |

**状态管理**是单品的表字段,后补需要改表结构并回填存量数据。**养护支出记账**是 CPW 分子的组成部分,不做则核心公式不完整,而它的成本只有一个表单和一条统计序列。这两项因此留在 V1.0。

**CPW 即时反馈评估后不做。** 原计划在记录穿搭后当场弹一句"这件的单次成本降到 ¥X 了"。放弃的理由不是成本,是**这个数字在单次记录的尺度上没有意义**:CPW 的分母是累计穿着次数,分子还随养护支出变动,一次穿着带来的变化既小又受太多因素影响。把它推到用户眼前,只会让人误以为"今天这一穿很划算",而真正该看 CPW 的时机是回看统计页、决定要不要再买一件同类的时候 —— 那里已经有完整的 CPW 榜和单次成本区间。**这是一次产品取舍,不是漏做。**

**语音备注原本推迟,实际提前做了。** 它服务的是北极星指标:记录门槛越低,周记录天数越高,而按住说一句话确实比打字快。技术上也不贵 —— `MediaRecorder` 录 webm/opus,和文字备注共用同一条存储路径。

**结构分析原本推迟,实际提前做了。** 它确实是纯展示层,但衣橱一到二三十件,"钱花在哪个品类""有多少件其实没在穿"这两个问题会先于 CPW 榜冒出来 —— 而它们只需要对已有数据做聚合,没有新的表结构成本。同批提前的还有支出趋势、衣橱规模、穿着分布、在穿比例、单次成本区间五张图。

### 五项模型能力的落地口径

抠图、AI 预填、水洗标 OCR、详情页提取、报告追问都已接通。下面几条口径与本文原文有出入,以此处为准:

**① 抠图用「商品分割」,不是通用分割。** 本文 6.2 写的是「调用第三方抠图 API」,没有指定类型。实测同一张挂在衣柜上的浅色纱裙:通用显著性分割(浏览器端 WASM 与本地 rembg)保留 0%,衣服被整个当成背景;阿里云「商品分割」保留 62% 且完整。区别不在精度,在**任务定义** —— 通用分割找「画面里显眼的东西」,会把衣架、手、页面按钮一起抠出来。

**② 抠图结果不覆盖原图,给用户选。** 背景杂或多件入镜时,抠出来的未必比原图好。默认用抠图,旁边留「原图」切换。抠图不喂任何评分维度,失败也不挡录入。

**③ 成分名由模型照抄原文,归并交给代码的别名表。** 本文 6.2 要求材质是结构化数据,但没说别名怎么办。实测水洗标上写的是「苎麻」「桑蚕丝」「真丝丝绒」,附录 D-2 的十四档里一个都没有 —— 不做映射的话这些衣服的材质全部读不出来。

别名表只收行业通用的同义叫法(苎麻/亚麻→麻,桑蚕丝/丝绒→真丝,涤纶→聚酯纤维…),拿不准的(莱赛尔、天丝)宁可不收,让它落到手填。**硬套一个相近的档会算错养护建议,而错的养护建议是真会把衣服洗坏的** —— 和 §8 不做材质图片识别是同一个理由。

归并前的原文存进 `Material.raw`,不参与算分,两个用途:养护建议按原文给(「苎麻:折痕处易发白」比「麻:注意收纳」有用);将来若要把「麻」拆成苎麻/亚麻两档,有真实分布可依据,不必让用户重录。

**④ 照片会离开设备。** 识别与抠图都要把照片发给服务商;登录后照片还会存进云端。口径是:围度、预算等数字未登录时只在本地;照片在使用识别时外发、处理完取回,服务商不留副本;不想外发可跳过识别手填。

告知方式:**首次触发识别或抠图时弹一次确认**,同意后不再打扰,可选"手动填写"跳过。不做每次勾选 —— 外发的是平铺单品照和电商截图,不含人像,为它设一道复选框是把摩擦全压在用户身上,拦不住任何风险;《个人信息保护法》第 23 条要的是**单独同意**,单独不等于重复。

弹窗里同时写明**什么不外发**:全身照与档案照片只存本机或用户自己的云端空间。只说"照片会发送至第三方",用户会默认包括他的全身照。

对外不点名具体服务商,只写"第三方识别服务"。**已改**（2026-08-31 绑自有域名对外时）—— 弹窗里点名了 DeepSeek 与阿里云视觉智能开放平台。依据仍是上面那条第 23 条：单独同意与告知接收方名称是同一条的两个要求。

批量上传、养护建议卡片仍是纯展示层,任何时候加都不影响存量数据。

**⑤ 追问的边界由代码挡,不靠提示词。** 6.6 要求"分数稳定可复现",而模型天然会顺着用户的话给结论、给估分。所以三件事在代码里挡在模型之前:结论性提问先被拦下(§8"不给购买建议");认出价格改动直接回规则引擎重跑;能对到某个维度的直接用报告里那一行。剩下的开放性问题才交给模型。提示词里也写了同样的规则,但那是第二道 —— 软约束绕过去一次,产品立场就没了。

**⑥ 颜色从图里取,不问模型。** 模型只返回色系(闭集),填进去的是"粉色"的固定示意色,藕粉和桃粉会变成同一个值。改为在浏览器里对上传的图取主色调:精确、免费、不外发。抠图成功时对透明底的不透明像素取,那是最准的一次。

### 账号与云端同步(V1.0 追加)

原计划全程只用浏览器本地存储。实际加了 Supabase,因为本地存储有两个躲不开的上限:
**一是 5MB 配额**,而每件衣服连图约 30KB,几十件加上 OOTD 全身照就会撑满;
**二是换设备就没了**,而"手机拍照录入、电脑上看统计"是这个产品的正常用法。

口径:**免登录可以完整使用产品**,数据存本地;想上云再登录,邮箱魔法链接,无密码。
登录入口在个人档案页,**不做登录页** —— 登录墙会让第一次来的人在看到任何东西之前
就要付出成本,而 §9 的第一指标是让人看懂 CPW,不是收集用户。

内置的演示衣橱**不上云**。它是给访客看的样例,传上去会污染衣橱重复度、总花费、
品牌排名与评分口径。

## 8. 功能边界(明确不做)

| 不做的事 | 原因 |
|---|---|
| **电商导购、跳转购买、分成返佣** | 与"理性消费"的产品价值观直接冲突,会让决策评分失去公信力。这是我们和搭搭、Lookie 最本质的分野,**不能妥协** |
| 社交/社区/关注体系 | MVP 是个人工具。搭搭已在社区上建立壁垒,我们不正面竞争,且社区会稀释核心价值 |
| 二手转卖、闲置交易 | 涉及交易、物流、纠纷,超出 MVP 范围 |
| 3D 虚拟试衣、AI 换装、数字分身 | 技术成本高,对核心问题(该不该买、穿够本没)帮助有限 |
| 资产折旧计算 | 规则难定义、用户难理解,CPW 已承担价值判断职责 |
| 通用商品识别 | 只做截图 OCR 提取,识别不准时降级为手填 |
| 材质图片识别 | 从照片判断成分不可靠,会给出错误的养护建议,反而害了用户的衣服 |
| 养护知识百科 | 只做上下文触发的提示,不做内容运营 |
| 原生 App(iOS/Android) | 先 Web,移动端浏览器响应式适配即可 |
| 多用户/家庭共享衣橱 | 单用户单衣橱,不做用户协作 |
| 智能搭配推荐 | 只做"可搭配性判断"(规则驱动,服务于决策),不做主动推荐 |
| 给出购买结论 | 只输出分数与分维度理由。决策主体是用户,引导性结论既超出评分参数能承担的权威,也与"不替用户做决定"的立场冲突 |
| 让对话替用户下结论 | 报告追问同样不给买/不买。被直接问到时把决定权还回去、摆出关键权衡,而不是给答案 —— 换个入口就松口,等于上一条没有 |
| 全站通用 AI 助手 | 对话只挂在购买评分的报告下,只答这份报告。摊开成什么都能问,上下文组装复杂,且更难守住上面两条边界 |
| 天气自动推荐 | 天气仅作为记录字段与决策参考,不做推荐引擎 |
| 男装品类支持 | MVP 聚焦女性,男装可录入但不做品类细分和专门的决策逻辑 |

## 9. 核心指标

| 层级 | 指标 |
|---|---|
| **北极星指标** | 周穿搭记录天数(用户每周记录了几天穿搭)—— 同时代表留存和数据质量 |

## 10. 规则口径

> 本节规则由设计、前端、后端共同遵循。口径不统一,三端会实现出不一致的结果,而"判断可复现"是决策评分公信力的前提。

### 附录 A:女装品类

粒度设计原则:**二级分类的粒度要刚好够支撑"衣橱重复度"判定**。粗到只有"内搭",会把衬衫和卫衣判成重复;细到"泡泡袖雪纺衬衫",则永远判不出重复。

一级 10 类、二级 94 项(去重 93,"开衫"跨两类共用)。每组末尾的"其他 X"是兜底项 —— 录入时找不到对应款式也能入库,不必逼用户瞎选一个。

| 一级品类 | 二级品类 |
|---|---|

| 外套 | 西装 / 夹克 / 牛仔衣 / 棒球服 / **开衫** / 风衣 / 大衣 / 斗篷 / 棉衣 / 羊羔绒 / 羽绒服 / 皮衣 / 皮草 / 其他外套 |
| 裤子 | 牛仔裤 / 休闲裤 / 运动裤 / 西装裤 / 打底裤 / 皮裤 / 其他裤子 |
| 半身裙 | 包臀裙 / 背带裙 / 蓬蓬裙 / A字裙 / 百褶裙 / 其他半身裙 |
| 连体装 | 连衣裙 / 连衣裤 |
| 鞋 | 高跟鞋 / 乐福鞋 / 长靴 / 踝、短靴 / 平底时装鞋 / 凉鞋 / 板鞋 / 帆布鞋 / 运动鞋 / 豆豆鞋 / 洞洞鞋 / 松糕鞋 / 懒人鞋 / 雪地鞋 / 休闲鞋 / 拖鞋 / 其他鞋类 |

| 配饰 | 手表 / 发饰 / 内衣 / 袜子 / 领带 / 腰带、腰链 / 围巾、披肩 / 丝巾 / 手套 / 眼镜 / 其他配饰 |

**上半身分内搭与外套两类。** 二者的搭配、养护、价位区间都不同,合成一类会让"西装外套配衬衫"这种最基本的搭配关系无法表达(同一品类内部不算互补),评分②的可搭配率会系统性偏低。

**"开衫"是唯一跨两类的二级品类** —— 冬天套在毛衣外当内搭的第二层、春秋直接当外套穿,两种用法都成立,由用户录入时自己归。代价是**二级品类名不再全局唯一**:所有"由二级反查一级"的逻辑都不成立,一级必须在录入时显式记录,不能从二级推。

**包、帽子、首饰、配饰纳入录入、CPW 计算与花费统计,但不参与"可搭配性"维度** —— 搭配互补矩阵只在 内搭 / 外套 / 裤子 / 半身裙 / 连体装 / 鞋 之间计算。

### 附录 B:CPW 计算

**CPW =(购买价格成本 + 累计养护支出)÷ 累计穿着次数**

| 场景 | 规则 | 理由 |
|---|---|---|
| 穿着次数 = 0 | 不显示 CPW,显示"尚未穿着 · 已投入 ¥X" | 显示 ∞ 或退化成购买价,都会污染排行榜和衣橱均值 |
| **衣橱平均 CPW** | (总购买支出 + 总养护支出)÷ 总穿着次数 | **不是**各单品 CPW 的算术平均 —— 算术平均会被"只穿过 1 次的贵外套"拉爆 |
| 已处置单品 | 不进 CPW 排行榜(榜单只含"在用"与"闲置"状态);仍计入累计购买支出与历史花费统计 | 榜单的行动含义是"该多穿它了",已送人 / 卖掉的单品无法行动 |
| 养护支出 | 发生即计入该单品 CPW 分子;月度趋势图中挂在支出发生月,与购买支出分列 | 单品详情页与统计看板两处的口径必须一致 |

### 附录 C:季节窗口

**季节窗口(全国统一):** 春 3–5 月 / 夏 6–8 月 / 秋 9–11 月 / 冬 12–2 月。

按城市气候带做差异化窗口更准确,但需维护城市–气候带映射表,且用户改城市时历史口径会变。V1.0 用统一窗口,后续版本可校准 —— 纯计算逻辑,不影响表结构。

**"本季还没穿过"的判定:**

```
当季 = 今天所属季节
单品季节标签 S ⊆ {春,夏,秋,冬};"四季"款 = 全集

若 当季 ∉ S                                 → 不纳入(冬装在夏天没穿是正常的)
若 当季 ∈ S 且 本季窗口内被 OOTD 关联次数 = 0   → 纳入"本季还没穿过"
```

### 附录 D:评分规则

**总分 = ①15 + ②20 + ③25 + ④20 + ⑤20**(⑤ = 5a 围度 14 + 5b 肤色 6)

维度不可算时(冷启动、商品无尺码表等)按可算权重归一:`总分 =(已算维度得分之和 ÷ 可算权重之和)× 100`,界面同时标注"本次评分基于 N 个维度(共 5 个)"。

所有输入(衣橱快照、预算余额、品类均价、CPW 中位数)在评分时刻取值,随决策记录一并存档,历史评分可复现。界面标注"基于 X 月 X 日的衣橱状态"。

参数表 D-1 至 D-4 为初始值,需在种子数据上试跑后校准。

#### ① 衣橱重复度(15 分)

相似判定:**二级品类相同 且 色系相同**。风格标签只作展示,不作判定条件。

| 相似件数 | 0 | 1 | 2 | 3 | ≥ 4 |
|---|---|---|---|---|---|
| 得分 | 15 | 11 | 7 | 3 | 0 |

修正:相似单品的平均穿着次数 < 3 时再扣 2 分(下限 0)。
输出:列出具体单品及其穿着次数与 CPW。

#### ② 可搭配能力(20 分)

可搭配 = 品类互补(D-3)且 颜色可搭(D-4)且 季节标签有交集。
**可搭配率 = 可搭配件数 ÷ 衣橱中互补品类的单品总数**(用比率而非件数,不受衣橱规模影响)。

| 可搭配率 | ≥ 60% | 40–59% | 25–39% | 10–24% | < 10% |
|---|---|---|---|---|---|
| 得分 | 20 | 15 | 10 | 5 | 2 |

#### ③ 价格合理性(25 分)

**主路径(衣橱 ≥ 15 件)**

| 子项 | 计算 | 分档 |
|---|---|---|
| 3a 品类均价(9 分) | 价格 ÷ 该二级品类历史均价 | ≤0.8→9 / 0.8–1.2→7 / 1.2–1.8→4 / 1.8–2.5→2 / >2.5→0 |
| 3b 预算占用(8 分) | 价格 ÷ 本月剩余预算 | ≤20%→8 / 20–40%→6 / 40–70%→4 / 70–100%→2 / 超支→0 |
| 3c 预估 CPW(8 分) | 价格 ÷ 该二级品类在用单品的年均穿着次数,再比衣橱 CPW 中位数 | ≤中位数×0.7→8 / ≤×1.0→6 / ≤×1.5→4 / ≤×2.5→2 / 更高→0 |

该品类历史不足 3 件时 3a 不计,9 分按比例摊给 3b、3c。

**冷启动路径(衣橱 < 15 件)**

`参考价 = 品类基准价(D-3) × 品牌档次系数(D-1) × 材质价格系数(D-2)`

| 价格 ÷ 参考价 | ≤0.8 | 0.8–1.2 | 1.2–1.8 | 1.8–2.5 | >2.5 |
|---|---|---|---|---|---|
| 得分 | 25 | 19 | 12 | 6 | 0 |

款式不参与打分 —— 审美判断无法规则化。由大模型在理由文本中提及,不影响分数。

#### ④ 材质与养护(20 分)

材质从三条路径影响 CPW:舒适度低会被闲置(压低分母)、耐久度低会提前退休(压低分母上限)、养护成本高会抬高分子。三者按 4 : 3 : 3 加权。

```
材质分(0–10) = Σ(占比×舒适)×0.4 + Σ(占比×耐久)×0.3 + Σ(占比×养护)×0.3
维度得分 = 材质分 × 2,需干洗再 −4(下限 0)
```

起球不单独扣分 —— 耐久度已经涵盖。
**年度预估养护成本** = 品类养护频次 × 单次成本(D-2),单独输出,不参与算分。

#### ⑤ 身材与肤色适配度(20 分)

分两个子项:**5a 围度贴合 14 分 + 5b 肤色适配 6 分**。

合成一个维度而不是新开第⑥个,有一个具体理由:5a 对**鞋 / 包 / 帽子 / 首饰 / 配饰完全不适用**(它们没有可比的围度),这五类原先在⑤上一分都算不了;而颜色与肤色的关系对它们反而更直接 —— 一条围巾、一顶帽子紧挨着脸,比一条裤子更吃肤色。并进来之后,这五类也有分可算。

**5a 围度贴合(14 分)**

差值 = 尺码表围度 − 用户围度。按品类取相关围度:内搭 / 外套 → 胸围 + 肩宽;裤子 / 半身裙 → 腰围 + 臀围;连体装 → 胸围 + 腰围 + 臀围;鞋 / 包 / 帽子 / 首饰 / 配饰不适用。

| 情况 | 得分 |
|---|---|
| 全部相关围度差值在 +2~+8cm(合理松量) | 14 |
| 有 1 项超出该区间,绝对偏差 ≤ 3cm | 10 |
| 有 1 项偏紧(< 0cm)或过松(> 15cm) | 6 |
| 2 项及以上超出 | 2 |
| 无尺码表数据 / 品类不适用 | 5a 不计,14 分按权重摊给其余可算项 |

**5b 肤色适配(6 分)**

肤色四档各自的冷暖倾向,与商品色系(D-4 的八档)的冷暖比对:

| 肤色档 | 色值 | 冷暖 |
|---|---|---|
| 白皙 | `#E5C0B0` | 偏冷 |
| 自然 | `#D9AC8D` | 中性偏暖 |
| 小麦 | `#BA8062` | 中性 |
| 深 | `#855743` | 偏暖 |

| 色系(D-4) | 冷暖 |
|---|---|
| 中性色 | 通用 |
| 红 / 橙 / 黄 / 棕 | 暖 |
| 蓝 / 紫 | 冷 |
| 绿 | 中性(军绿偏暖、薄荷偏冷,合并归中) |

| 情况 | 得分 |
|---|---|
| 商品是中性色,或与肤色冷暖一致 | 6 |
| 一方为中性(肤色中性 或 色系中性) | 5 |
| 冷暖相反 | 3 |
| 用户未设肤色 | 5b 不计,6 分摊给其余可算项 |

> **冷暖相反只扣到 3 分,不归零。** 这是全套规则里**最软的一条判断** —— 肤色与颜色的搭配没有公认口径(四季色彩理论有好几个流派),结果还随光线和妆容变。它的位置是"提醒你注意一下",不是"你不适合穿这个颜色";重罚等于产品替用户否掉了一整个色系,与 6.6"不替用户做决定"的立场冲突。
>
> 同样出于这个原因,**5b 的理由文本要写成参考语气**("蓝色系偏冷,与你的暖调肤色对比较强"),不写成结论("不适合你")。

### 附录 E:OOTD 排序

单品由用户自己勾选,本规则只决定勾选界面中衣橱单品的**排列顺序**。衣橱到 50 件以上时,按录入时间排列会让用户每天翻三屏才能找齐 4–6 件,而这一步直接决定第 9 节"关联率 > 80%"能否达成。

排序优先级,依次应用:

1. **当季衣服优先** —— 季节标签含当季的单品排在前
2. **近期穿过优先** —— 其中最近 30 天有穿着记录的再往前提,按最近穿着日期倒序
3. **同现搭档优先** —— 已勾选任一单品后,与它在历史 OOTD 中同时出现过的单品实时提到前列

V1.0 用纯规则排序,零 API 成本且结果可预测。由大模型从 OOTD 全身照识别候选的方案留到 V1.1 —— 体验更好,但每次记录多一次视觉调用,且识别失败会卡住记录流程。
